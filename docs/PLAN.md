# HushQuote — Plan of Record

> **Any model/session working on this project: read this file, IDEAS.md and UI.md first.
> Do not deviate without updating this file and noting why in the Decisions log.**

## One-liner
Speak a job description; a local open-weight model running **entirely in your browser** turns it into an itemized, editable, professional quote — then a branded PDF. No account. No server. Your clients and rates never leave your device.

## Why it fits "Side Hustle"
- Real person: tradespeople + freelancers (the archetypal side hustlers).
- Specific problem: quoting is slow, hated, and lost quotes = lost income.
- They already pay: invoicing SaaS is $10–30/month.
- Open-source AI is load-bearing, not decoration: privacy of client data + rates, offline use on job sites, zero running costs (no API bill for a side hustler).

| UI | **Tailwind v4** (UI.md tokens as `@theme`) + **Radix primitives** (Dialog, Toast only) + **lucide-react** + self-hosted **Inter variable** | Bespoke paper aesthetic, no component kit (REVIEW M3) |

## Core flow (3 steps, one primary action per screen)
1. **Describe** — mic button + textarea. Example chips ("bathroom tiling job", "logo design package"). Model streams structured JSON.
2. **Review** — itemized quote table: editable qty/rate/description, auto totals, tax toggle. Model suggestions visually distinct until confirmed (dashed border → solid on accept).
3. **Send** — branded PDF preview, download/share. Business profile (name/logo/rates) editable inline, saved locally.

## Model contract
- Prompt → strict JSON schema: `{ client?, items: [{description, qty, unit, rate?}], notes? }`
- Rates resolved from the user's saved rate library first; model fills gaps, UI marks guesses as "estimate — tap to set".
- **Never let the model invent totals** — all math done in app code. (Writes well in the DEV post: "the LLM extracts, the app calculates".)
- Graceful degradation ladder: WebGPU (WebLLM) → WASM (wllama) → no-model manual mode (same UI, user types line items). App is never broken.

## Non-goals (do not scope-creep)
- No accounts, no backend, no payments integration, no email sending.
- No multi-currency/locale matrix — one currency selector, done.
- No invoice numbering schemes/accounting features — it's quotes first; "Mark as invoice" just changes the PDF title.
- No model fine-tuning talk in the post unless actually done.

## Competitive landscape (D4 dev.to research, for the D5 post)
Searched dev.to's Week 2 "Side Hustle" submissions for overlapping ideas.
Several close neighbors, all freelancer/local-business finance tools:
**InvoicePilot AI** (Ollama + Qwen2.5 + PaddleOCR + Python/FastAPI backend
+ SQLite), **VaultLedger AI** ("100% local, air-gapped" invoice/finance
OS), **FreelanceAI** (invoice/receipt sorter, local), **Clausler**
(air-gapped AI contract auditor). All of them are desktop-process
architectures: Ollama or a Python backend the user has to install and run
alongside the app. **HushQuote's actual differentiator is the delivery
model, not just "runs locally"** - it is the only one of this group that
is a pure static PWA: no backend, no install, no local server process: the
model downloads into the browser tab itself (wllama/WASM+WebGPU) and runs
there. "No install" is a stronger, more verifiable claim than "runs
locally" when the competition's "local" still means "install and run
Ollama first." Lead the DEV post with this, not just the privacy angle.
Also relevant as a citation: dev.to/sharpenlee's "Why LLMs return invalid
JSON" (see docs/RISKS.md R3's D4 research note) - directly explains and
confirms the truncation failure mode this project hit and fixed, good
supporting evidence for the "the LLM extracts, the app calculates"
section of the post.
Also noted: the challenge rubric (dev.to challenge id 80) confirms both
"Best Use of Gemma" and "Best Use of Render" are separate $200 featured
categories a single project can enter - deploying to Render (still
blocked, see D1/D4 notes below) is not just infra, it is a second prize
category on top of Gemma.

- 2026-10-14 (pre-deploy code tightening): Two real bugs found and fixed on a full code pass:
  1. **Example chips could silently corrupt onboarding.** `handleExampleChip` called the real model when ready - tested all three sample transcripts live and every one produced 2-4 fabricated extra lines (duplicate/garbled fragments, or the few-shot example's "Materials/Labor/Callout" leaking in), even on the already-verified-good ones from the RISKS.md sweep. Root cause is the model's baseline behavior, not wording - tried three rewordings of the logo chip, all failed the same way. Fixed by making chips always seed a known-correct line directly (`EXAMPLE_ITEMS`), never calling the model - matches docs/UI.md rule 6's actual intent ("sample data," not "live demo of real failure modes" on a new user's first tap). Also swapped the "logo package" chip for "fence staining" (test transcript 16, confirmed reliable) since every flat-fee phrasing tried failed the same way regardless of wording.
  2. **Silent whole-quote/profile/rate-library data loss.** Found a reproducible pattern: the tax-rate inputs (Sheet.jsx, ProfileDrawer.jsx) and the rate-library rate input had no bounds, but their zod schemas do (`taxRate` in [0,1], `rate` nonnegative, `qty` positive, `description` non-empty). zod's `safeParse` rejects the WHOLE object if any one field is out of range, and `loadJSON` falls back to an empty default on that rejection - so typing "500" into a tax field, or clearing a line's description, silently wiped the entire saved quote (or profile, or rate list) on the next reload, with no error shown. Fixed at the choke points: `QuoteContext`'s reducer now clamps qty/rate/description on every `ITEM_ADDED`/`ITEM_EDITED`, clamps `taxRate` on `TAX_SET`; `RatesContext.updateRate` clamps rate; both tax inputs also clamp at the UI layer. Verified live: typed 500% tax, cleared a description, confirmed in both cases the saved quote survives a reload intact instead of reverting to empty.
